## 0. 一分钟结论（给 lead）

- 基线核心闭环确实能走通：起服务 → 灌入消息 → 收件箱 → 回复（Mock 标注）→ 状态流转 → 全链路回放 → 待办 → 账号页 → 新建发送，全部走了一遍，没有崩。
- 「Mock 不伪装真实」这一点做到了：`模拟发送（未调用真实平台）`、`模拟状态回流（本地 Mock）`、账号页 Mock Tag、投递方式标注，都能看见。

  1. 配了账号到底通不通？——账号页说「真实接口 / 已配置」，哪怕 App ID 是假的；只有 doctor 才说 FAIL。（P1-1）

## 2. 第一天必卡的三件事

> 以「一个只会双击和粘贴的普通同事」为视角，按实际卡住时长排序。

1. **前置环境就是第一道墙（未完全实测，因为本机已装好）**：机器上如果没装 Node.js，双击 `start.bat` 只会得到一行 `[ERROR] Node.js not found. Install Node.js 20+ from https://nodejs.org`（英文，窗口会停住）。用户得自己去官网下载、安装、可能还要重启终端；README 没有一步到位的「Windows 装 Node」指引。装完后 `pnpm` 仍需 corepack 启用并**重开终端**（quickstart 有写，但小白普遍会忽略"重开终端"）。
2. **配完 `.env`，看不出到底生效没有**（P1-1 / P1-5）：账号页显示「真实接口 / 已配置」，但 App ID 是假的也这么显示；改完 `.env` 不重启，页面和接口完全不变，也没有任何"请重启服务"提示。用户会以为"我配了没用"或"我填错了"，然后开始乱改。
3. **空收件箱没有下一步**（P1-3）：README 说空收件箱会出现「3 步上手」（含可复制的 `python scripts/smoke.py` 命令），实际页面只显示「还没有收到消息」和三个平台胶囊（看起来像筛选标签）。用户不知道要先"灌一条示例消息"，很可能就此放弃，认为"没消息=坏了"。

### P1-1 账号页显示「真实接口 / 已配置」，但凭据是假的也不报警；README 却让用户看账号页判断"生效没有"

- **现象**：填了一个假的飞书 App ID/Secret 后，账号页显示「真实接口 · 已配置 · 飞书凭据可用 → auto 解析为真实接口」，没有任何"连不通/凭据无效"的提示。
- **我做了什么**：按 README「换一个账号，只要 3 步」填假凭据 → 重启后端 → 打开「平台账号」页。
- **我以为**：页面会告诉我"飞书已连上"或"飞书连不上，去 doctor 看原因"。
- **实际**：页面只按"环境变量格式是否齐全"显示，`/api/accounts` 返回 `configured=true / mode=real / canReceive=true / canSend=true`，但同一时刻 `pnpm run doctor --platform=feishu` 明确 FAIL：`10003 invalid param：App ID 不存在或应用已被删除`。两边结论相反。
- **证据**：
  - 截图 `docs/qa/screenshots/phase1-baseline/13-accounts-fake-feishu-real-mode.png`
  - 账号页文本：`飞书 / 真实接口 / 已配置 / 飞书凭据可用 → auto 解析为真实接口`
  - doctor 输出：`[FAIL] 飞书 tenant_access_token（应用凭据校验）… 飞书返回错误码 10003（invalid param）`
  - README 第 288 行原文：判断是否生效最快的方式…「或在浏览器『平台账号』页看每个平台的 configured / 收 / 发」——**这条建议会误导**。
- **建议**：
  - 账号页对 `mode=real` 的平台增加"最近一次真实连接结果/最近一次发送结果"（无记录时明确写「尚未验证，请点 doctor 自检」），别只显示"已配置"；
  - 或直接在卡片上给「运行自检」按钮/一键复制 `pnpm run doctor --platform=feishu`；
  - README 把"看账号页判断生效"改成"看 doctor 的 PASS/FAIL"，账号页只用来确认"填了/缺什么变量"。

### P1-2 真实模式发送失败：toast 说「已提交发送」，失败原因只在回放深处；消息详情不说原因

- **现象**：真实模式（假凭据）里点「新建发送」→ 发送 → 弹窗关闭，toast 显示「已提交发送，可在『全链路回放』查看状态回流」（读起来像成功）；过几秒消息才变成「发送失败」。
- **我做了什么**：新建发送 → 填会话 `oc_whatever` + 文本 → 点发送。
- **我以为**：要么提示"发送成功"，要么弹红字告诉我哪里错了。
- **实际**：
  - toast 是成功口吻：「已提交发送，可在『全链路回放』查看状态回流」；
  - 消息详情页只有「回写失败，已写入死信队列」「可修改内容后再次发送；生产环境会按指数退避重试 3 次。」——**没有错误原因**；
  - 真正原因（`飞书 tenant_access_token 获取失败: 10003 invalid param`；另一种情况是「飞书当前是真实模式（FEISHU_MODE=real），但缺少 FEISHU_APP_ID / …。可运行 pnpm run doctor 自检，或把 FEISHU_MODE 设为 mock 先本地演示。」）只在点「回放」后的闭环日志里。
- **证据**：
  - 截图 `15-send-failed-detail.png`、`16-trace-send-failed.png`、`18-compose-missing-creds-error.png`、`19-trace-missing-creds.png`
  - 详情页文本只有：`回写失败，已写入死信队列 / 可修改内容后再次发送；生产环境会按指数退避重试 3 次。`
  - 回放里才出现：`飞书当前是真实模式（FEISHU_MODE=real），但缺少 FEISHU_APP_ID / FEISHU_APP_SECRET / FEISHU_VERIFY_TOKEN。可运行 pnpm run doctor 自检…`
- **建议**：
  - 发送失败时 toast 用失败口吻，并带一句人话原因（可截断）+「查看详情」；
  - 消息详情页「发送失败」区域直接显示 `failedReason`（后端已有日志文本，展示成本低）；
  - 异步提交成功与异步发送成功要区分文案：前者写「已提交，正在发送…」，不要用可能被读成已成功的「已提交发送」；
  - 给失败消息一个显眼的「重试」按钮，而不是让用户改内容再发。

### P1-4 `pnpm doctor` 静默无输出、退出码 0，看起来像"自检通过"

- **现象**：按直觉敲 `pnpm doctor`（少写 `run`）→ **终端没有任何输出，退出码 0**，耗时 0.2 秒。
- **我做了什么**：`cd unimsg-connector` → `pnpm doctor`。
- **我以为**：doctor 跑完了、没问题。

- **证据**：命令输出为空、`EXITCODE=0`；同目录 `pnpm run doctor` 输出完整报告（见 `doctor-noenv-out.txt` 记录）。

  - 或在 README 的「换账号 3 步」代码块里直接写全 `pnpm run doctor` 并从标题/第一行强调（现在已经有，但埋在下方 ⚠️ 里）；

### P1-5 改完 `.env` 不重启，页面/接口完全不变，也没有任何"需重启"提示

- **现象**：我改好 `.env`（填飞书假凭据）后不重启，刷新账号页——仍然显示「Mock 模拟 / 未配置 / 缺少 FEISHU_APP_ID…」，和改之前一模一样。
- **我做了什么**：编辑 `.env` → 刷新页面 → 调 `/api/accounts`。
- **我以为**：保存 `.env` 后刷新页面就能看到新状态。
- **实际**：运行中的后端只在启动时读 `.env`；页面没有任何"配置已变更，请重启服务"的提示。新手最常见的反应是"我是不是填错位置/填错拼写"，然后重复改半天。
- **证据**：
  - 截图 `12-accounts-after-env-edit-no-restart.png`（改完未重启仍显示未配置）
  - 同时刻 `/api/accounts` 返回 `mode=mock, configured=false, missing=[FEISHU_APP_ID…]`；重启后才变成 `mode=real`
- **建议**：
  - 账号页展示 `.env` 文件的**修改时间**，并与"服务启动时间"比对；不一致时在页顶提示「.env 已修改，需重启后端生效」；
  - 启动器/文档在"改完必须重启"处加粗并配一条现成命令；
  - doctor 报告里也提示"以下为磁盘配置；运行中的服务需重启才生效"。

### P1-6 点「连接飞书用户身份」整页跳走；授权失败只在飞书页显示错误码，回 LinkHub 无任何提示

- **我做了什么**：账号页 → 点「连接飞书用户身份」→ 观察标签页变化。
- **我以为**：会弹一个小窗让我登录授权，或者至少回到 LinkHub 后告诉我"授权失败/没权限"。
- **实际**：整页跳转；失败时用户看到的是飞书侧的裸错误码（英文/数字，不是本产品的中文提示）；返回后无任何反馈，也不知道要找谁/改什么。
- **证据**：
  - CDP target 截图：`page | 飞书授权 | https://accounts.feishu.cn/open-apis/authen/v1/authorize?client_id=…`，页面文本 `错误码：20028`

### P2-1 新建发送要填「目标会话 ID（chat_id / open_id）」技术 ID，小白不知道从哪拿；错误文案又叫 `conversationId`

- **现象**：弹窗字段「目标会话 ID（留空则复用该平台最近会话）」，placeholder 是「飞书 chat_id（oc_…）或单聊 open_id」；留空点发送报「向 feishu 发送缺少目标会话：请填写 conversationId，或先让该平台收到一条消息」。
- **我做了什么**：不填会话直接发；随后随便填了个字符串再发。
- **我以为**：要么能选一个联系人/群，要么告诉我到哪复制这个 ID。
- **实际**：要手填平台内部 ID，小白根本不知道在哪找；错误文案里的 `conversationId` 和输入框里的 `chat_id/open_id` 又不是同一个词；"或先让该平台收到一条消息"对新用户是死循环（收不到消息才来发）。
- **证据**：截图 `08-compose-modal.png`、`09-compose-sent.png`；错误文本如上。
- **建议**：提供"最近会话"下拉（已有消息/会话时自动列出可选）；没有历史会话时给出"如何获取 chat_id"的折叠说明或平台跳转链接；统一术语。

### P2-2 回复发送成功后再点一次会真的重复发送（无二次确认、输入框不清空）

- **现象**：回复发送成功后，底部输入框仍保留原文「收到，我会在截止前完成。」，发送按钮仍可点；再点一次后 trace 里出现**两轮** processing→replied→sent→synced，等于真的又发了一遍。
- **我做了什么**：发送成功后手滑再点一次「发送回复」。
- **我以为**：会提示"已发送过"或按钮置灰。
- **实际**：又发了一次（Mock 下无害并如实标注；真实模式下会重复打扰对方）。
- **证据**：截图 `05-trace-replay.png`（10 条事件、两轮 sent/synced）；toast 再次「已提交回写，状态将实时更新」。
- **建议**：发送成功后清空输入框/禁用按钮 2 秒，或对同一条消息的重复回复做二次确认；回放里可去重展示。

### P2-3 连接成功状态只有一颗绿点，quickstart 让看的「已接入 LinkHub Server」文字实际看不到

- **实际**：visibility 上看不到；只有绿点。quickstart 第 51/69 行、README 的表述已过期。
- **证据**：截图 `02-inbox-with-messages.png`（左下角只有绿点）；CDP 查到 `aria-label="真实后端：已接入 LinkHub Server"`；断线时页面可见「已离线」（截图 `25-token-mismatch-401.png`）。

## 6. 做得好的地方（避免只挑刺，给评审/队友参考）
